# Deployment runbook

The repository implements the supported Phase 2 lifecycle; no production deployment or live AWS archive certification was performed. Use a staged rollout with separate test accounts.

1. Provision Node 24, Java 21, PostgreSQL 18, SMTP, TLS ingress and secret management. The web and worker are separate managed processes. Keep the pinned TypeScript runner available for worker/migration scripts. Install Java from a verified distribution; the developer's ignored macOS Temurin directory is not a portable dependency.
2. Install with `npm ci` and `npm run compliance:install`. Set absolute `JAVA_BIN` and `COMPLIANCE_HOME`. The installer verifies pinned downloads and individual rule files and records `installation.json`; the worker verifies them again. Mount rules/runtime read-only. Retain the manifest and installed artifacts for each issued profile. Do not fetch `latest` at runtime.
3. Provision a private bucket with versioning, Object Lock and default KMS encryption in the approved region. Set `ARCHIVE_MODE=S3_OBJECT_LOCK`, `AWS_REGION`, `ARCHIVE_BUCKET`, `ARCHIVE_KMS_KEY_ARN`. Use workload identity and a dedicated KMS key. The application verifies configuration, per-object COMPLIANCE retention, concrete version and encryption metadata, then reads back exact bytes. Never configure automatic deletion at the default retention timestamp without assessing longer obligations.
4. Limit the runtime to its bucket/prefix and required `GetBucketVersioning`, `GetBucketObjectLockConfiguration`, `GetEncryptionConfiguration`, `PutObject`, `PutObjectRetention`, `GetObject`, `GetObjectVersion`, `GetObjectRetention` and KMS encrypt/data-key/decrypt rights as required by your provider. Do not grant DeleteObject/Version, bucket-policy administration, retention bypass, key deletion or general account administration. Enforce TLS and conditional writes through bucket policy where supported. Confirm exact permission names and behavior in the target S3 implementation; S3 compatibility alone does not prove Object Lock support.
5. Set `APP_ENV=staging` or `production`, HTTPS `BETTER_AUTH_URL`, fresh `BETTER_AUTH_SECRET`, `DATABASE_URL`, `SMTP_URL`, `MAIL_FROM`. Never deploy test mode. Build with safe environment injection, take a database backup, run forward-only `npm run db:migrate` using the migration identity and apply reviewed `scripts/runtime-grants.sql` for a separate non-owner runtime identity. No schema push.
6. Run `npm start` behind TLS and `npm run worker` under an unprivileged service account. The JVM has code-level URI restrictions, 256 MiB heap, a single active processor and 30-second timeout. Also configure host/container filesystem/network restrictions and a realistic RSS/CPU budget. Node needs database/object-storage connectivity; Java receives no service credentials and should not have outbound network access. Do not claim that a JVM heap limit alone is container confinement.
7. Allow at least 180 seconds graceful shutdown. Outbox claims expire after 180 seconds; failed handlers back off and dead-letter after eight attempts. Monitor queued-job age, pending finalizations, dead letters, archive integrity failures, validator timeouts, DB saturation and disk capacity. Allowlisted logs expose correlation and duration. OpenTelemetry instruments need your chosen SDK/exporter; none exports data by default.
8. Run `npm run archive:reconcile` with an operational identity. It pages through documents, verifies pinned bytes, appends checks and exits nonzero on integrity failure. It reports stale jobs without deleting objects. `npm run archive:reconcile -- --retry-failed` requeues recoverable jobs older than five minutes when no delivery is active. Investigate unknown profiles, stale snapshots and validation failures instead of forcing them. Known staged objects are retained even without a document row; repeating the same job conditionally reuses and verifies them.
9. Before live invoices: run all tests against a disposable DB; validate actual bucket Object Lock/IAM denial behavior; exercise upload-success/DB-failure recovery; verify missing/corrupt object alerts; restore encrypted DB and object versions together; verify SMTP confirmation/reset, hostile origins, secure cookies, roles and tenant rejection. Preserve independent audit-chain heads outside the DB. Configure backup retention, residency, legal holds and incident response with accountable owners.

Local development remains at web `http://localhost:3000`, PostgreSQL `localhost:5432`, Mailpit SMTP `localhost:1025`, Mailpit inbox `http://localhost:8025`. Development requires email verification; test-only loopback browser fixtures bypass it. A local archive is clearly identified as development storage and is refused in staging/production. Credentials, original invoices, temp XML and local databases must not be committed or packaged into images.

Upgrade a profile by reviewing official production sources and licenses, adding a new immutable manifest/install directory, exercising the full valid/invalid corpus, migration and recovery suite, reviewing changes in normalized issues, then selecting the new profile for new jobs. Drain old jobs with their matching worker version. Never rewrite historic XML or change a stored ruleset identity to the current version.
