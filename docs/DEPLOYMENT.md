# Deployment runbook

The repository implements the supported Phase 2 lifecycle; no production deployment or live AWS archive certification was performed. Use a staged rollout with separate test accounts.

1. Provision Node 24, Java 21, PostgreSQL 18, SMTP, TLS ingress and secret management. The web and worker are separate managed processes. Keep the pinned TypeScript runner available for worker/migration scripts. Install Java from a verified distribution; the developer's ignored macOS Temurin directory is not a portable dependency.
2. Install with `npm ci` and `npm run compliance:install`. Set absolute `JAVA_BIN` and `COMPLIANCE_HOME`. The installer verifies pinned downloads and individual rule files and records `installation.json`; the worker verifies them again. Mount rules/runtime read-only. Retain the manifest and installed artifacts for each issued profile. Do not fetch `latest` at runtime.
3. Provision a private bucket with versioning, Object Lock and default KMS encryption in the approved region. Set `ARCHIVE_MODE=S3_OBJECT_LOCK`, `AWS_REGION`, `ARCHIVE_BUCKET`, `ARCHIVE_KMS_KEY_ARN`. Use workload identity and a dedicated KMS key. The application verifies configuration, per-object COMPLIANCE retention, concrete version and encryption metadata, then reads back exact bytes. Never configure automatic deletion at the default retention timestamp without assessing longer obligations.
4. Limit the runtime to its bucket/prefix and required `GetBucketVersioning`, `GetBucketObjectLockConfiguration`, `GetEncryptionConfiguration`, `PutObject`, `PutObjectRetention`, `GetObject`, `GetObjectVersion`, `GetObjectRetention` and KMS encrypt/data-key/decrypt rights as required by your provider. Do not grant DeleteObject/Version, bucket-policy administration, retention bypass, key deletion or general account administration. Enforce TLS and conditional writes through bucket policy where supported. Confirm exact permission names and behavior in the target S3 implementation; S3 compatibility alone does not prove Object Lock support.
5. Set `APP_ENV=staging` or `production`, HTTPS `BETTER_AUTH_URL`, fresh `BETTER_AUTH_SECRET`, `DATABASE_URL`, `SMTP_URL`, `MAIL_FROM`. Never deploy test mode. Build with safe environment injection, take a database backup, run forward-only `npm run db:migrate` using the migration identity and apply reviewed `scripts/runtime-grants.sql` for a separate non-owner runtime identity. No schema push.
6. Run `npm start` behind TLS and `npm run worker` under an unprivileged service account. The JVM has code-level URI restrictions, 256 MiB heap, a single active processor and 30-second timeout. Also configure host/container filesystem/network restrictions and a realistic RSS/CPU budget. Node needs database/object-storage connectivity; Java receives no service credentials and should not have outbound network access. Do not claim that a JVM heap limit alone is container confinement.
7. Allow at least 180 seconds graceful shutdown. Outbox claims expire after 180 seconds; failed handlers back off and dead-letter after eight attempts. Monitor queued-job age, pending finalizations, dead letters, archive integrity failures, validator timeouts, DB saturation and disk capacity. Allowlisted logs expose correlation and duration. OpenTelemetry instruments need your chosen SDK/exporter; none exports data by default.
8. Run `npm run archive:reconcile` with an operational identity. It pages through documents, verifies pinned bytes, appends checks and exits nonzero on integrity failure. It reports stale jobs without deleting objects. `npm run archive:reconcile -- --retry-failed` requeues recoverable jobs older than five minutes when no delivery is active. Investigate unknown profiles, stale snapshots and validation failures instead of forcing them. Known staged objects are retained even without a document row; repeating the same job conditionally reuses and verifies them.
9. Before live invoices: run all tests against a disposable DB; validate actual bucket Object Lock/IAM denial behavior; exercise upload-success/DB-failure recovery; verify missing/corrupt object alerts; restore encrypted DB and object versions together; verify SMTP confirmation/reset, hostile origins, secure cookies, roles and tenant rejection. Preserve independent audit-chain heads outside the DB. Configure backup retention, residency, legal holds and incident response with accountable owners.

Local development remains at web `http://localhost:3000`, PostgreSQL `localhost:5432`, Mailpit SMTP `localhost:1025`, Mailpit inbox `http://localhost:8025`. Development requires email verification; test-only loopback browser fixtures bypass it. A local archive is clearly identified as development storage and is refused in staging/production. Credentials, original invoices, temp XML and local databases must not be committed or packaged into images.

Upgrade a profile by reviewing official production sources and licenses, adding a new immutable manifest/install directory, exercising the full valid/invalid corpus, migration and recovery suite, reviewing changes in normalized issues, then selecting the new profile for new jobs. Drain old jobs with their matching worker version. Never rewrite historic XML or change a stored ruleset identity to the current version.

## Vercel deployment boundary (ERechno)

Use `apps/web` as Root Directory, Next.js preset and Node **24.x**. Enable **Include source files outside of the Root Directory in the Build Step**: the shared package sources, root lockfile and TypeScript configuration are required. `apps/web/vercel.json` installs with `cd ../.. && npm ci` and builds with the workspace `npm run build`; its prebuild prepares the pinned browser OCR/PDF assets even when the root npm script is bypassed. Output is `.next`, and tracing includes the monorepo root. Dependencies stay hoisted at the root. No build script executes migrations or starts a worker.

Before deployment, provision the external PostgreSQL database and a provider pooler. Use a pooled URL for web and worker (transaction pooling must support the SQL transactions/row locks used here); run migrations using a separate direct connection and migration-owner role. TLS must verify the server certificate (`sslmode=verify-full`); a provider with a private CA needs its trusted certificate/root installed rather than disabling verification. Runtime pools are reused in each warm web instance and limited to two clients each, including a separate two-client billing pool when enabled. A provider pooler and global connection budget are still required as Vercel scales instances.

Run migrations explicitly from the repository root: take a backup, set APP_ENV=production and DATABASE_URL to the verified direct migration URL, then `npm run db:migrate`. The migrator serializes concurrent migration runners using a session advisory lock. Apply reviewed `scripts/runtime-grants.sql` and, if using billing, `scripts/billing-grants.sql` with admin credentials. Use distinct non-owner runtime/billing identities afterward. Never put migration credentials in Vercel and never run schema push during build. Test migrations against a disposable copy before applying them to live data.

The persistent worker (`npm run worker`) belongs on a managed VM/container with Node 24, Java 21 and pinned KoSIT files installed by `npm run compliance:install`. Vercel handlers enqueue validation, issuance, incoming XML/PDF checks and invoice delivery; web reads archive objects and uploads incoming bytes directly to durable S3. The worker consumes the existing durable DB outbox, performs both readiness and issuance validation, archives immutable XML, extracts embedded ZUGFeRD XML in an isolated Node child process, sends invoice mail, consumes audit-related events and runs periodic financial/autopilot reconciliation. Neither a JVM nor PDF subprocess validation runs in a normal web request. An explicit web validator guard throws if that boundary is crossed. No separate network validator service is required: Java runs on the worker host. Monitor pending job age/dead letters; deploying web alone leaves these required business processes pending, so do not onboard live invoices until the worker is healthy.

Keep S3 versioning, Object Lock COMPLIANCE retention and KMS configured and test actual permissions/read-back integrity. Local archive storage is development-only. Ephemeral temporary worker files are processing scratch, never the invoice archive. Immutability controls do not by themselves certify full GoBD compliance; preserve organizational controls, backups and restore tests described above.

Create environment names from `docs/PRODUCTION-ENVIRONMENT.md`. For the first deployment set APP_URL and BETTER_AUTH_URL to the same stable assigned HTTPS Vercel project origin; after manually connecting erechno.de and verifying TLS, update both to https://erechno.de. Secure cookies are already enabled for HTTPS, trusted origins are limited to the configured auth origin, and reset/verification redirects use that origin. Preview requires its own stable configured origin and isolated resources. Domain DNS is not changed by these repository preparations.

External prerequisites: PostgreSQL with pooler/backups and separate migration/runtime roles; private AWS S3 Object Lock bucket and KMS/IAM access for web and worker; authenticated TLS SMTP with verified auth/invoice senders; managed worker hosting with Java and pinned KoSIT distribution. Stripe and a separate billing role are additionally required only if billing is enabled; an invoice gateway is optional. Public launch also needs real legal/support/company details.

Next manual action in Vercel: keep project `erechno`, Root Directory `apps/web`, Next.js preset; enable outside-root source inclusion and select Node 24.x. Check that install/build overrides match apps/web/vercel.json, then add the Production/Preview settings from the inventory. Do not press Deploy until required services and migration/grants are ready. No deployment or Namecheap DNS change was performed by this task.

The first ERechno Production/Preview database provisioning is now complete: both isolated Frankfurt Neon projects have the 12 repository migrations and restricted `flux_runtime` roles. Their pooled URLs are sensitive Vercel variables scoped to their own environment. Provisioning admin inputs were cleared and removed. Later migrations still require a separately provided migration identity; never use the runtime role or repeat initial role provisioning just to apply another migration.

Hosted preflight verifies the actual Node TLS socket and certificate authorization. On TLS-terminating PostgreSQL proxies, `pg_stat_ssl` reports the backend hop and does not prove whether the client connection was encrypted. URL validation still requires `sslmode=verify-full`; no certificate validation is disabled. `apps/web/vercel.json` now selects the single Frankfurt Function region (`fra1`) to keep web DB traffic close to both Neon projects.
