# ERechno worker and archive deployment assets

No service or paid resource is created by these files.

`erechno-worker.service` runs the existing worker on an EU Linux VM with systemd. Install Node 24 at `/opt/node24`, deploy this monorepo at `/opt/erechno`, install dependencies once with `npm ci`, and install Java 21 from its official distribution. Run the repository's pinned `compliance:install` step during provisioning, not web builds. Place the assets under an absolute COMPLIANCE_HOME readable by the dedicated `erechno` service account, and keep the deployment/assets read-only. The installer writes files with mode 0600, so explicitly grant the service account read access; do not make secrets world-readable.

Create the unprivileged `erechno` Linux user/group. Supply actual secrets through root-managed `/etc/erechno/worker.env` (mode 0600), using the environment inventory. It needs APP_ENV=production, DELIVERY_FROM, JAVA_BIN and COMPLIANCE_HOME plus the common production DB/archive/mail/auth settings. The database must be a restricted non-owner runtime role. For an AWS-hosted VM use a narrow instance role instead of static keys; another host needs its own scoped AWS identity. Do not reuse another application's credentials or database.

The unit performs read-only provider/schema checks before starting, isolates scratch files in a private temporary directory, limits memory to 1.5 GiB and permits up to 180 seconds graceful shutdown. Node/Java JIT remain supported; this unit does not pretend a JVM heap bound is a complete sandbox. Systemd itself is not available on this macOS workstation, so validate the unit with `systemd-analyze verify` on the target host before enabling it. Configure host egress/network restrictions, restore tests, job-age/dead-letter alerts and resource monitoring independently. No host was provisioned or unit activated by this preparation.

`npm run production:check` checks the actual database connection's TLS, non-admin/non-owner role, expected schema columns and visibility, S3 versioning/Object Lock/KMS configuration, and SMTP authentication. `npm run production:check -- --worker` additionally validates an in-memory controlled fixture with the pinned KoSIT validator. No email, database row, archive object or fiscal invoice is created. Provider errors are redacted. These checks do not prove actual retention/IAM-denial behavior or full migration constraints; run the existing archive recovery/immutability corpus and a separately approved staged storage test before live invoices.

`archive-runtime-policy.json` is an unapplied least-privilege template. Substitute the actual bucket, concrete KMS key ARN and region obtained from your AWS resources. Attach it to separate dedicated application identities, not unrelated IAM users. No delete/version delete, governance bypass, retention administration, bucket administration, KMS key deletion or account-wide rights are granted. Ensure the KMS key policy allows the intended identities; enforce TLS via bucket policy. Test versioned retrieval, conditional writes, COMPLIANCE retention and denied deletions with controlled data. Do not apply it until the owner provisions the paid archive resources. Production and Preview need separate retained buckets/credentials and no access to each other's data.
